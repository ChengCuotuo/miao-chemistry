# Windows 自动更新：更新源托管与接入方案

> 对应分支：`develop-builder-win`（`electron-builder.yml` + `scripts/build-windows.mjs` 已就位）
> 前置事实：现在构建产物里**只有** `miao-chemistry-Setup-<version>.exe` 和它的 `.blockmap`，**没有** `latest.yml` —— 所以目前这套文件不会被任何程序读取。

## 一、先分清两种「托管」

| 目的 | 需要托管什么 | 现在能不能做到 |
| --- | --- | --- |
| 只想要稳定的下载直链（用户手动装） | exe（blockmap 可选） | 已经可以：GitHub Release + Gitee 同步 |
| 想让应用自己检查更新、自动装 | exe + `.blockmap` + `latest.yml` 三者同源 | 需要先配 `publish` 并接 electron-updater |

自动更新能不能工作，取决于**更新源上有没有 `latest.yml`**：它是更新元数据（版本号、发布日期、每个文件的 sha512 与大小）。没有它，更新器无从判断有没有新版本。

## 二、关键机制（三条，先看懂再动手）

1. **`publish` 配置 = 更新源地址，并且会被固化进安装包。**
   electron-builder 会把解析后的 publish 配置写到应用包里 `resources/app-update.yml`（源码：`PublishManager` → `outputFile(path.join(resourcesDir, "app-update.yml"), ...)`）。
   含义：**改了更新源必须重新打包**，光上传文件不起作用。

2. **没有 `publish` 配置（且仓库识别不出 GitHub）就不会生成 `latest.yml`。**
   源码 `getPublishConfigsForUpdateInfo()` 里只做一件事：识别出仓库类型是 `github` 时，即使没写 publish 也补一份默认配置（注释写明「file should be generated regardless of publish state」）。
   你们的 `.git/config` 里 `origin` 是 Gitee、`package.json` 里也没有 `repository` 字段，所以识别结果为「无」→ 不生成 yml。这与实际构建产物一致。

3. **三个文件必须同源，且历史文件不能删。**
   `latest.yml` 里按**文件名**索引 exe 与 blockmap；差分更新时还要向服务端取「旧版本安装包的 blockmap」。所以更新源目录要长期保留各版本的 exe 与 blockmap，只覆盖 `latest.yml`。

## 三、更新源选哪条路线

electron-updater 内置的 provider 只有：`github`、`gitlab`、`bitbucket`、`generic`、`keygen`（另有 `PrivateGitHub`）。**没有 gitea / gitee 的 provider**。

| 路线 | 配置 | 优点 | 代价 |
| --- | --- | --- | --- |
| GitHub Releases | `provider: github` + `owner` / `repo` | 最省事，CI 里 `--publish always` 一条命令就传完了 | 更新包要从 GitHub 下载，国内教师机器上可能很慢或失败 |
| 静态目录 / 对象存储（推荐） | `provider: generic` + `url` | 国内速度可控（OSS/COS/七牛/自建站点都行）；与现有 GitHub/Gitee Release 分发互不干扰 | 需要自己维护一个固定目录并覆盖上传 `latest.yml` |
| Gitee Release 直链 | 只能当 `generic` 的 url 用 | 国内可达 | `generic` 要求 `latest.yml` 在一个**固定 URL** 上（`${url}/latest.yml`），而 Gitee 附件直链按 tag 变化，因此不能直接把 release 附件地址当作 url，需要自己做个固定入口 |

结论建议：**用 `generic` 指向一个国内可达的固定目录**，`latest.yml` 每次覆盖，exe 与 blockmap 只增不删。

## 四、落地清单

### 1. 装依赖

```bash
yarn add electron-updater
```

注意：你们主进程是 Vite 打包的、asar 里不带 `node_modules`，所以 `electron-updater` 需要能被 Vite 打进 `main.js`。装好后先用 `npx electron-forge package` 确认产物能正常加载（打包后启动一次即可验证）。

### 2. 配置 publish

```yaml
# electron-builder.yml（generic 路线）
publish:
  provider: generic
  url: https://<你的静态目录>/miao-chemistry/updates/
```

```yaml
# 或者 GitHub 路线
publish:
  provider: github
  owner: ChengCuotuo
  repo: miao-chemistry
```

建议**显式写**，不要依赖自动推断（源码里对「从 CI 环境或 .git/config 推断出来的 feed」会打 warning：`specify it explicitly to be sure it stays under your control`）。

### 3. 主进程接上更新逻辑（最小可用）

```js
// src/main.js
import { autoUpdater } from 'electron-updater';

app.whenReady().then(() => {
  // 静默检查：有新版本会在后台下载，下次退出时安装
  autoUpdater.checkForUpdatesAndNotify();
});
```

要点：
- 你们的 `oneClick: false`（向导演示式安装）在更新时由 electron-updater 传 `isSilent` 静默调起安装包，不需要用户点向导。
- 更新流程会**退出应用再重启**，所以别在退出流程里拦截退出；本轮加的单实例锁不影响这一点。
- 覆盖安装路径与手动安装一致，数据目录不变（`%APPDATA%\miao-chemistry`），不会丢积分数据。

### 4. 发布时上传三个文件

构建完成后，更新源目录里应该是这样（文件名必须与 `latest.yml` 里登记的一致）：

```
/updates/latest.yml                                  ← 每次覆盖
/updates/miao-chemistry-Setup-2.0.3.exe
/updates/miao-chemistry-Setup-2.0.3.exe.blockmap
/updates/miao-chemistry-Setup-2.0.2.exe              ← 历史版本保留
/updates/miao-chemistry-Setup-2.0.2.exe.blockmap
```

两种上传方式：
- GitHub 路线：`electron-builder ... --publish always`（CI 里需要 `GH_TOKEN`）。
- generic 路线：保持现在的「构建 → 上传产物」流程，在 CI 里加一步把 `latest.yml`、exe、blockmap 一起推到静态目录。

## 五、必须注意的坑（按代价排序）

1. **未签名**：自动更新是让程序自装自启，未签名包更容易被杀软拦截或 SmartScreen 拦下，失败率明显高于手动安装。**建议先把签名做掉再开自动更新**（`CSC_LINK` / `CSC_KEY_PASSWORD`）。
2. **`BUILD_TYPE` 会退化成 trial**：workflow 里 `github.event.inputs.build_type || 'trial'`，tag 推送时实际会打出 30 天试用版。开了自动更新后，这等于把正式版用户「更新」成试用版 —— 后果很严重，务必先修（改成 `|| 'official'`）。
3. **文件名必须对齐**：`latest.yml` 里的文件名与上传的文件名要完全一致。你们 CI 有一步把所有产物平铺到 `release/`，若中途改名会直接导致更新失败。
4. **频道 / 预发布**：tag 里带 `-` 时 CI 会把 Release 标成 prerelease，而 `latest.yml` 只索引正式版本；正式版 tag 要保证不含 `-`。
5. **只覆盖 `latest.yml`**：历史 exe 与 blockmap 删了以后，差分更新会退化为全量下载（能装，但每次都要下 ~91 MB）。
6. **更新源要能匿名 GET**：对象存储记得开公共读；Gitee 附件直链的匿名可达性需要实测（部分需要登录或带 token）。
7. **首次「迁移到自动更新」的一版仍需手动装**：已经装在用户机器上的老版本不含更新逻辑，所以必须有一次手动安装把入口带上；从那之后的版本才能自动更新。

## 六、如果暂时不想开全自动：轻量替代方案

对「教师在课堂上不能被打断」的场景，半自动更稳妥：应用启动时请求一个静态 `version.json`（自己维护，比 `latest.yml` 简单），发现新版本就在界面里提示「有新版本，点击下载」，跳转到 GitHub/Gitee 下载页由用户手动安装。

这个方案不需要 `publish`、不需要 electron-updater、不需要 blockmap，也不受签名影响，可以先落地；等签名到位、更新源稳定后再升级成全自动。

## 七、验证顺序（建议）

1. 加 `publish` 配置 → 本地构建，确认产物里出现 `latest.yml`，并确认安装后 `resources/app-update.yml` 内容正确。
2. 打包 2.0.3 上传到更新源，机器上留有 2.0.2 → 启动应用，看日志是否报「发现新版本 / 下载 / 安装」。
3. 故意删掉 `.blockmap` 再测一次，确认回退为全量下载（日志会打 `Cannot download differentially, fallback to full download`）。
4. 最后在没有网络的机器上试一次，确认失败不阻塞应用使用。
