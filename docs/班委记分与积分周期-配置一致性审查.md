## 1. 运行时修改基础设置的风险点(逐条)

### R1 · 关闭「启用班委记分」后,在线班委仍能记分且跳过审批 【P0】

**触发条件**:班委已登录 → 管理员在基础设置关闭「启用班委记分」。

**现状**:
1. 班委的 tab 只判断角色,不判断任何开关--`grade/index.vue:88` `if (isMonitor.value) return name === 'monitor';`
2. 周期记分页的可记分状态也不看开关--`MonitorList/index.vue` `canRecord = !!currentCycle && status===0 && rules.length>0`
3. 数据层入口**完全不校验角色与开关**--`useMonitorCycle.ts` `adjustPointsByRule` 的校验只有:班级存在、周期存在、周期未结束、时间范围、规则存在/有分值(grep 结果:无 `currentRole` / `monitorAccountEnabled` / `monitorApproval` 判断)
4. 提交时是否走审批由这个表达式决定--`MonitorList/index.vue` `submitNeedsApproval = isMonitor && monitorAccountEnabled && approvalEnabled`

**后果**:开关关闭后,在线班委的 `submitNeedsApproval` 变成 `false` → `adjustPointsByRule` 走 `!isPending` 分支 → **立即 `student.points += points`,记录 `status=1`**。也就是:本该"谁都不能记分"的状态下,积分被直接写进去了,且不留待审批痕迹。

**修复建议(推荐)**:在数据层兜住,而不是只靠界面:
- `adjustPointsByRule` 增加校验:`submitter` 存在(班委提交)且 `basicConfig.monitorAccountEnabled === false` → 返回 `{ success:false, message:'已关闭班委记分,无法提交' }`
- 同时在 `MonitorList` 给已登录班委一个明确的只读态(横幅提示 + 禁用记分按钮),而不是让他点下去才报错

### R2 · 关闭「启用班委记分」后,残留待审批记录卡死 【P1】

**现状**:审批入口与弹窗都挂在 `monitorAccountEnabled` 上--`MonitorList/index.vue` 工具栏按钮 `v-if="!isMonitor && monitorAccountEnabled"`,弹窗同理。

**后果**:关闭开关前若还有待审批记录,关闭后**再也没有入口**去通过/驳回它们;数据仍在(`status=0`),学生也拿不到分。

**当前缓解**:关闭时的二次确认文案里提醒「若还有未处理的待审批记录,请先处理完」--但只是提醒,不拦截。

**修复建议(二选一)**:
- A:关闭前统计待审批条数,有则**阻止关闭**并提示条数;
- B:审批入口门控改成 `monitorAccountEnabled || 存在待审批记录`(把"有事没处理完"作为例外)。

> 注意 A 方案有个实现难点:待审批记录存在各班级的 `grade-{id}.json` 里,基础设置页拿不到,需要在关闭时异步读取各班数据,成本略高。B 方案改动小、无数据读取。**我倾向 B**。

### R3 · 关闭「周期记分」模块后的连带问题 【P1】

**现状**:
- 教师侧 tab 隐藏--`grade/index.vue:91` `if (name === 'monitor') return monitorVisible.value;`
- 但**班委侧 tab 不受该开关约束**--`grade/index.vue:88` 只看 `isMonitor`
- 数据分析隐藏依赖该开关--`grade/index.vue:95`
- 关联分组 / 独立分组隐藏「积分周期」选择器,且记分不再归入周期(`source=0`)--`GroupList/index.vue:492`、`TeamList/index.vue:290,312`

**后果**:模块关闭后,教师再也进不了周期记分页 → 待审批记录同样卡死(与 R2 同类);同时一个"模块已关闭"的系统里,班委仍能看到并使用周期记分页。

**修复建议**:把 `monitorAccountEnabled` 与 `monitorManage` 一起纳入 `isTabVisible` 的班委分支;审批入口按 R2 的 B 方案兜底。

### R4 · 关闭审批开关后,已有待审批记录与入口语义矛盾 【P1】

**现状**:`monitorApproval` 只影响"新提交是否进待审批"(`MonitorRecordModal.needApproval`、`submitNeedsApproval`)。审批入口只看 `monitorAccountEnabled`,所以关闭审批后**入口照旧显示「待审批记录(N)」**,里面的旧记录仍是待审批状态。

**歧义**:管理员关闭"需管理员审批"的直觉预期是"以后不用审了",可能连带认为"之前的也算通过了",但系统不会自动通过。

**修复建议**:关闭审批开关时给出明确提示(例如:「已有 N 条待审批记录需要你手动审批,关闭开关不会自动通过它们」),或提供「关闭并全部通过」的选项。

### R5 · 「重新开始」对已过期周期实际无效 【P1】

**现状**:
- 过期判定只看状态与日期--`useMonitorCycle.ts` `isCycleExpired`: `status === 0 && endTime && today > endTime`
- 教师点「重新开始」→ `startMonitorCycle` 把 `status` 置 0(`useMonitorCycle.ts`)
- 但 `MonitorList` 进入页面时(也含 `GroupList`/`TeamList`)会调 `autoFinishExpiredCycles()`,把所有"进行中且已过期"的周期重新置为已结束

**后果**:重新开始一个时间范围已过去的周期 → 状态刚变进行中,立刻(或下次进页面)又变已结束。用户看到的是"点了没用",而数据层 `adjustPointsByRule` 的时间校验也会拒绝记分(`已过期`)。

**歧义**:「重新开始」的语义到底是"恢复记分"还是"延长时间"?目前的实现等于"只有当周期时间范围还没结束时才能恢复"。

**修复建议**:二选一--
- A:重新开始时若已过结束时间,弹窗要求填写新的时间范围(语义清晰,推荐);
- B:`isCycleExpired` 增加"被手动重新开始过则不再自动结束"的标记(引入新字段,成本高且难解释)。

### R6 · 改周期时间范围会改变历史记录的周期归属 【P1】

**现状**:`source=0`(教师普通记分)的记录**没有 `cycle_id`**,归入哪个周期完全靠时间范围匹配:
- 数据分析:`recordInCycle`--`source === 1` 用 `cycle_id`;否则 `if (!cycle.startTime || !cycle.endTime) return false` 再比日期(`AnalysisList/index.vue`)
- 积分记录弹窗:同一套逻辑(`RecordList/index.vue` `studentRecords` 内注释明确写了这条规则)

**后果**:编辑周期时间范围(允许,见下)会把一批历史 `source=0` 记录**重新划归**到该周期,趋势分析、周期记录列表的数字会变。反之,给"无时间范围"的周期补上时间范围,会一次性把历史记录吸进来。

**歧义**:周期是"时间段"还是"批次"?目前是混合语义:班委记录按批次(`cycle_id`),教师记录按时间段。

**修复建议**:短期在编辑时间范围时提示「会重新归属该时间段内的普通记分记录」;长期建议给 `source=0` 的记分也写入当前周期 `cycle_id`(若在周期内记分),统一为批次语义。

### R7 · 周期结束后审批仍入账,会改动"已结算"周期 【P1 · 业务决策】

**现状**:`approveRecords` 不校验周期状态(这是上次你确认的"结束后仍可审批"),通过即 `student.points += points`。

**歧义**:周期通常在结束后被当作"结算完成"--排行榜、奖励发放可能已按当时的周期积分执行。事后审批会改变该周期成绩,但系统没有任何"已结算"标记或提示。

**修复建议**:至少给"周期已结束后再审批"加一次二次确认,提示「该周期已结束,通过后将改变该周期的积分成绩」;是否引入"锁定结算"作为更强的保护,建议单独讨论。

### R8 · 删除周期静默删除待审批记录 【P1】

**现状**:`deleteMonitorCycle` 无条件删除该周期全部 `source=1` 记录(三种状态都删),确认文案只提了"删除所有积分记录 + 回退积分"(`MonitorList/index.vue:397`),未提待审批。

**后果**:班委已提交但未审批的记分被无声删除;班委端的"我的待审批"计数凭空减少,且没有任何提示。

**修复建议**:删除确认弹窗中追加「其中包含 X 条待审批记录,将一并删除」,并为"已驳回记录同时被删"给出说明。

### R9 · 自动结束周期由"进入页面"触发,班委也会触发 【P2】

**现状**:`autoFinishExpiredCycles()` 在三处页面 `onMounted` 被调用--`MonitorList`(教师与班委共用)、`GroupList`、`TeamList`。

**歧义**:周期状态变更(写数据)由"打开页面"这个只读行为发起;而且**班委进入周期记分页也会触发**,与"周期管理仅管理员"的设定不符。多人同时打开时以先进入者为准,结果虽然一致,但语义上不干净。

**修复建议**:把自动结束收敛到教师侧(或在班委端只做"过滤掉过期周期"的展示处理,不写数据)。

### R10 · 待审批保护会让记录数超过 1000 上限 【P2】

**现状**:`trimRecordList` 裁剪时把全部待审批记录无条件保留,非待审批取最近 `1000 - pending.length` 条;若 pending ≥ 1000,则只留 pending,总数仍可能超 1000。

**歧义**:「保留最近 1000 条」这个口径现在变成了"1000 条 + 待审批"。正常使用(待审批个位数)无影响,属可接受取舍,但需要知道上限被打破了。

### R11 · 删除班委账号不影响其在线会话 【P2】

**现状**:`verifyMonitorAccount` 只在登录时校验(`useMonitorAccount.ts`);账号被删后,已登录会话的 `currentMonitor` 仍保留(`app.ts` `currentMonitor`),提交记录仍写入 `submitter_id`(指向已删除账号)+ 名称快照。

**歧义**:删除账号的预期是"这个人不能再记分",但实际必须等他退出/重启才失效。

**修复建议**:提交时校验 `submitter_id` 是否仍存在于 `monitorAccountList`,不存在则拒绝并提示重新登录。

### R12 · 数据层不校验"已结束周期不可删除" 【P2】

**现状**:`deleteMonitorCycle` 无状态校验;UI 在 `handleDeleteCycle` 里判断 `status === 1` 时拦截。

**歧义**:业务规则只落在 UI 层,绕过界面即可删除已结束周期(连带回退积分)。

**修复建议**:把该判断下沉到 `deleteMonitorCycle`(返回 `false` + 原因),UI 文案不变。

## 2. 三块功能的边界歧义(不全是 bug,而是需要写清楚的语义)

| # | 项 | 现状 | 歧义点 | 建议 |
| --- | --- | --- | --- | --- |
| A1 | 周期结构 | `source=1` 按 `cycle_id`(批次)、`source=0` 按时间范围(时间段) | 一个周期同时是"批次"和"时间段",改时间范围会改归属(见 R6) | 统一为批次语义,或明确写进手册 |
| A2 | 谁能记分 | 班委只能在**未结束**且**在当前时间范围内**的周期记分;教师走同一入口,因此**教师也不能给已结束周期补记** | "管理员应能补救"?目前不能 | 若需要,给管理员开"补记"通道并标记异常来源 |
| A3 | 审批与周期状态 | 周期结束 ≠ 审批结束;审批可在周期结束后入账 | 周期"结束"到底是不是"结算完成" | 加"已结算/锁定"概念或至少二次确认(见 R7) |
| A4 | 待审批记录的可见性 | 周期记录里能看见,但不计入学生积分、不进图表与导出 | 学生/家长视角看到记录却没加分,易误解 | 记录列表待审批行加更显眼的"未生效"标注 |
| A5 | 「原始提交人」列 | 教师自己记分的记录:`operator_name` 与 `submitter_name` 都写成"管理员" | 该列语义是"班委提交人",教师记录应留空 | 教师记录该列显示 `-` |
| A6 | 拒后不可重提 | 驳回是终态,不提供修改重提 | 班主任想让班委"改对了再报"只能让对方重新记一条新记录 | 手册写清楚;若需要重提,需新增状态而非复用 |
| A7 | 审批时"编辑"与"驳回"的关系 | 编辑只改内容、不改状态,改完仍是待审批 | 有人会以为"编辑=修改后直接通过" | 编辑保存后给出明确提示"仍待审批,需再选择通过/驳回"(当前 toast 已说明,可再显眼) |
| A8 | 开关组合的语义 | 三个开关:周期记分模块 / 启用班委记分 / 需管理员审批 | "关掉审批"≠"关掉班委记分",反之亦然,容易混 | 基础设置里补一段组合说明(README 14.4 已加,建议界面内也给 tooltip 组合表) |
