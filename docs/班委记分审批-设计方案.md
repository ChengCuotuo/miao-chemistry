## 1. 目标与范围

**目标**：班委在周期内通过规则提交的记分，不再直接生效，先进入「待审批」；管理员（教师角色）审批通过后才真正计入学生积分，驳回则永久不入库。

**范围内**：

- 班委角色在「周期记分」标签页提交的记分（`adjustPointsByRule` 是唯一入口）

**范围外**：

- 教师自己记分（含周期记分页里教师操作的记分、独立分组 TeamList 的记分）——教师即管理员，无需自审
- 多级审批、审批人分配、审批流配置
- 已通过记录的撤回（列为二期候选）

---

## 2. 现状（改造前数据流）

```
班委登录(锁屏选班委 → 班级 + 账号密码)
  └─ 周期记分页(MonitorList, 仅 monitor 标签可见)
       └─ 选周期 → 选学生/多选/按组 → 规则记分弹窗(MonitorRecordModal)
            └─ useMonitorCycle.adjustPointsByRule()
                 ├─ 校验：周期未结束、在时间范围内、规则存在、无分值规则必须有本次分值
                 ├─ 立即 student.points += 规则分值 × 次数        ← 直接生效
                 └─ push RuleRecord{ source:1, cycle_id, group_id, count }
```

关键事实：

- 记录与学生积分**同时**写入，没有中间态。
- `deleteMonitorCycle()` 靠 `recordList` 里 `source===1 && cycle_id===id` 的记录回退积分（`student.points -= record.points`）。
- `recordList` 只保留最近 1000 条（`slice(-1000)`）。
- 记录展示（RecordList）取规则名是 `rule?.name || '主动执行'`，已删规则会退化显示。
- 班委只能看到 `monitor` 一个标签页；教师可见全部标签页。
- 周期状态：0 进行中 / 1 已结束；班委只能对未结束周期记分。

## 3. 核心设计

### 3.1 状态机

```
                  ┌──────────── 管理员驳回（可填理由）
班委提交 ──▶ 待审批 ├──▶ 已驳回（不入库，永久保留痕迹）
 (0)        (pending)└──────────── 管理员通过
                              └──▶ 已通过（此刻才 +学生积分，写审批时间）
```

- 只有「待审批」可被审批；「已通过 / 已驳回」为终态（一期不做状态回退）。
- 状态挂在**单条记录**上，不做整批审批单：一条记分一次审批，粒度最细，批量操作只是 UI 层的多选。

### 3.2 数据模型

`RuleRecord` 新增字段（全部可选，确保旧数据反序列化不报错）：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `status` | number | 0 待审批 / 1 已通过 / 2 已驳回。**缺失或 undefined 一律视为 1（已通过）** |
| `operator_id` | string | 当前操作人 id（列表「操作人」列取这里的 name） |
| `operator_name` | string | 当前操作人名称：班委账号名，或教师操作的「管理员」 |
| `operator_role` | string | `monitor` / `teacher`，区分班委提交与教师操作 |
| `submitter_id` | string | **原始提交班委**账号 id（`MonitorAccount.id`），永不因修改而丢失 |
| `submitter_name` | string | 原始提交班委账号名快照（账号被删/改名后仍可追溯） |
| `audit_time` | string | 审批时间 `YYYY-MM-DD HH:mm:ss`，待审批为空 |
| `reject_reason` | string | 驳回理由，仅驳回时有值 |

**为什么 `status` 缺失默认是「已通过」而不是「待审批」**：历史记录（含 `source=0` 的普通记分）都已生效并计入学生积分，若默认成待审批，会出现「积分已加但状态显示待审批」的错乱。

`RuleRecord.toJSON()` 同步补这 5 个字段。

### 3.3 入库时机（最关键的一条）

| 动作 | 学生积分 | 记录 | 周期记录可见性 |
| --- | --- | --- | --- |
| 班委提交（审批开启） | **不变** | 新增 `status=0` | 可见，标「待审批」 |
| 管理员通过 | `+= 记录 points` | `status=1` + `audit_time` | 标「已通过」 |
| 管理员驳回 | **不变** | `status=2` + `reject_reason` | 标「已驳回」 |
| 班委提交（审批关闭） | 立即 `+=` | `status=1` | 标「已通过」 |

即：**积分只在审批通过的那一刻入账**。驳回天然不需要回退，因为从未加过。

### 3.4 操作人规则（含审批时修改）

「操作人」是这次新增的一条审计规则，语义如下：

| 场景 | 操作人 | 原始提交人 |
| --- | --- | --- |
| 班委提交 | 该班委账号 | 同左 |
| 管理员直接「通过」（未改内容） | 仍为该班委（保留痕迹，用于追责/统计） | 该班委 |
| 管理员审批时**修改**过内容 | **变为管理员** | 仍为该班委（不丢） |
| 管理员驳回 | 仍为该班委（驳回不是「修改」） | 该班委 |
| 教师本人记分（不经班委） | 管理员 | 管理员 |

- 修改入口：仅在「待审批」状态开放；**修改不改审批状态**，改完仍是待审批，由管理员再选通过或驳回。
- 修改范围：学生 / 规则 / 次数 / 本次分值（改后重算该条总积分；只改次数时按原单次分值等比换算）。
- 界面区分：操作人为管理员且原始提交人非空时，列表标记为「管理员（已修改）」。
- 展示：记录列表直接展示 `operator_name`；原始提交人在审批弹窗与记录详情里可见。

### 3.5 已有逻辑必须适配的点

| # | 位置 | 现状 | 改造 | 风险 |
| --- | --- | --- | --- | --- |
| 1 | `useMonitorCycle.adjustPointsByRule` | 直接加分 + 写记录 | 审批开启且提交者是班委时：只写 `status=0` 记录，不加分 | 核心改动点 |
| 2 | `useMonitorCycle.deleteMonitorCycle` | 用所有 `source=1` 记录回退积分 | **只回退 `status=1`** 的记录；pending/rejected 不参与。周期删除时三态记录一并删除 | ⚠️ 不改会误扣分：驳回记录没加过分，却会被扣一次 |
| 3 | `MonitorList` 学生列表积分列 | 直读 `student.points` | 不变（显示的是真实积分）；另在「学生周期详情」里增加待审批/已驳回分项 | 教师需要知道「已定积分」与「待定」的区别 |
| 4 | `MonitorList.detailStats`（学生周期规则统计） | 汇总 `source=1` 全部记录 | 拆成 已通过 / 待审批 / 已驳回 三列或加状态标签，合计口径明确 | 否则合计与真实入库不符 |
| 5 | `RecordList`（周期记录弹窗） | 无状态/操作人概念 | 增加「状态」「操作人」两列 + 状态筛选；驳回行显示理由 tooltip | 周期记录弹窗同时被班委使用（只读） |
| 6 | `AnalysisList`（趋势/行为画像/个体诊断/规则健康度/矩阵/导出） | 按 `source` 过滤统计 | 统一只统计 `status=1`；班委待审批数据不进图表，也不进 Excel 导出 | 若不改，图表与学生积分对不上 |
| 7 | `recordList` 1000 条截断 | `slice(-1000)` | 截断前**优先保留全部 pending**，只对非 pending 记录做 1000 条裁剪 | ⚠️ 不改会吞掉还没审批的提交，班委白干 |
| 8 | `MonitorRecordModal` / 提交处文案 | 「记分」 | 审批开启时按钮改为「提交审批」，提交后 toast：「已提交 N 条，等待管理员审批，**尚未计入积分**」 | 班委必须明确知道没生效 |

### 3.6 配置开关

`basicConfig` 新增两个开关，均默认 `true`（字段缺失也按开启处理），落点在「基础设置」页（与「隐藏减分快捷键」同区）：

| 开关 | 字段 | 默认 | 作用 |
| --- | --- | --- | --- |
| 启用班委记分 | `monitorAccountEnabled` | 开启 | 是否允许班委参与记分。**关闭后**：不能创建班委账号、锁屏页不显示「班委登录」、周期记分页隐藏「班委账号」与「待审批记录」入口，只能管理员自己记分 |
| 班委记分需管理员审批 | `monitorApproval` | 开启 | 班委提交是否先入待审批。关闭后班委提交直接生效（等同改造前行为） |

依赖与联动：

- 两个开关都依赖「周期记分」模块（`moduleVisibility.monitorManage`）已开启，否则置灰并提示
- 审批开关依赖「启用班委记分」：未启用班委记分时审批开关置灰（无人可提交）
- 关闭「启用班委记分」时二次确认，提醒先处理完未审批记录（关闭后审批入口隐藏）
- 关闭开关不会改动已存在的待审批记录数据；重新开启后仍可继续审批

## 4. 接口设计（`useMonitorCycle`）

新增/修改：

```ts
// 修改：提交时按角色与开关决定是否走审批
adjustPointsByRule(params: {
  cycleId: string; ruleId: string; students: Student[];
  groupId?: string; count?: number; pointsPerCount?: number;
  // 新增：
  submitter?: { id: string; name: string };   // 班委账号（教师提交时不传）
  needApproval?: boolean;                      // 由调用方按开关 + 角色传入
}): Promise<{ success: boolean; message: string; pendingCount?: number }>

// 新增
getCycleRecords(cycleId?: string, status?: number): RuleRecord[]
getPendingRecords(cycleId?: string): RuleRecord[]
countPendingRecords(cycleId?: string): number
approveRecords(ids: number[]): Promise<{ approved: number; pointsSum: number; message: string }>
rejectRecords(ids: number[], reason: string): Promise<{ rejected: number; message: string }>
// 审批时修改（仅待审批可改；修改后操作人变管理员，状态仍为待审批）
updatePendingRecord(
  id: number,
  patch: { stu_id?: string; rule_id?: string; count?: number; points?: number },
  operator?: { id?: string; name?: string },
): Promise<{ success: boolean; message: string }>
```

`approveRecords` 内部逐条：找到 `status===0` 的记录 → 对应学生 `points += record.points` → `status=1`、`audit_time=now` → 最后统一 `saveGradeInfo` 一次。
`rejectRecords` 内部逐条：`status=2`、`reject_reason`、`audit_time=now`，**不touch 积分**。

## 5. UI 设计

### 5.1 班委端（周期记分页）

- 记分弹窗按钮：审批开启时显示「提交审批」。
- 提交结果 toast：「已提交 N 条记录，等待管理员审批（尚未计入积分）」。
- 顶部周期提示条追加一行：`本周期你有 X 条待审批、Y 条已驳回`（X>0 时用警示色）。
- 「周期记录」弹窗里可看到自己提交记录的状态，驳回行显示理由。

### 5.2 教师端（周期记分页）

- 工具栏新增按钮：**待审批记录 (N)**，N>0 时用橙色/红色角标；N=0 时置灰但仍可点开看历史审批。
- 审批弹窗：
  - 默认筛选「待审批」，可切换「已通过 / 已驳回 / 全部」
  - 筛选维度：周期、班委、学生、规则、时间范围
  - 列表列：提交时间 / 周期 / 原始提交人 / **操作人** / 学生 / 规则 / 次数 / 单次分值 / 合计 / 状态 / 操作
  - 单条操作：**编辑**、通过、驳回（驳回弹输入框填理由，必填校验）
  - 编辑：可改 学生 / 规则 / 次数 / 本次分值，保存后「操作人」变为管理员（状态仍为待审批），再决定通过或驳回
  - 批量：多选 → 批量通过 / 批量驳回；批量驳回统一填一个理由
  - 顶部统计：「选中 N 条，合计 +12 / -3 分」
  - 通过后 toast：「已通过 N 条，学生积分已更新」，并刷新学生列表
- 学生周期详情弹窗：新增「待审批」「已驳回」两列，与「已通过」分开展示。

### 5.3 基础设置

- 新增开关「班委记分需管理员审批」，**默认打开**（字段缺失也按开启处理），带 tooltip 说明：「开启后，班委提交的记分需管理员在周期记分页审批通过后才计入学生积分」。
- 开关关闭后：班委提交直接入库（恢复改造前行为）；已存在的待审批记录不受影响，仍可审批。

## 6. 边界与异常处理

| 场景 | 处理 |
| --- | --- |
| 周期结束时仍有待审批 | 结束前弹确认框提示「还有 N 条待审批记录」；**结束后仍可审批**（审批是教师动作，不受周期状态限制），通过后积分照常入账 |
| 周期被删除 | 三态记录一并删除；**只回退 `status=1` 的积分** |
| 周期重新开始 | 待审批记录保持待审批，不做特殊处理 |
| 记录被 1000 条截断 | 优先保留 pending（见 3.4 #7） |
| 同一学生被多条记录命中 | 审批按条独立生效，互不影响 |
| 记录的规则后来被删除 | 展示沿用现状（规则名退化），审批不受影响（分值已存在记录里） |
| 旧数据无 `status` | 视为已通过，不出现「历史记录突然待审批」 |
| 关闭审批开关后 | 新提交直接入库；历史 pending 仍需审批 |
| 学生积分显示 | 只有已通过才计入；学生/小组列表、排行榜、图表口径一致 |

## 7. 非目标

- 不做审批退回后「修改再提交」（驳回后只能重新提交一条新记录）
- 不做已通过记录的撤回/冲正（二期候选，若做则提供「撤销通过 + 回退积分」）
- 不做审批通知（应用离线，无推送）
- 不改班委的权限边界（仍只能记分、不能改周期、不能删记录）
- 不影响独立分组的周期记录（教师操作，无审批）

## 9. 测试要点

1. 审批开启：班委提交后 `student.points` 不变，记录 `status=0`
2. 通过 1 条 → 积分 +1 条量；驳回 1 条 → 积分不变，理由落库
3. 批量通过/驳回混合选择，计数与积分变化正确
4. 删除周期：pending/rejected 记录不参与回退（**回归重点**）
5. `recordList` 超过 1000 条时 pending 仍完整保留
6. 审批开关关闭 → 直接入库（回归到改造前行为）
7. 旧数据（无 `status`）打开页面不报错、统计口径正确
8. 周期结束后仍可审批 pending
9. 图表（行为画像/规则健康度/趋势/个体诊断）与 Excel 导出不含 pending
10. 班委端可见范围与文案正确（明确「未计入积分」）

## 10. 评审结论落地情况

见文首「0. 评审结论」表。数据层已按结论实现并通过断言（37 项）：

| # | 已实现 | 断言证据 |
| --- | --- | --- |
| 1 | `RuleRecord.operator_*` 与「操作人」语义 | 班委提交后操作人 = 班委账号 |
| 2 | `basicConfig.monitorApproval` 默认 `true` | 字段缺失时按开启处理 |
| 3 | 审批不校验周期状态 | 周期已结束后通过仍入账 |
| 5 | 驳回为终态，不可再通过、不可修改 | 已驳回记录 approve/update 均被拒 |
| 6 | 无撤回 | 未提供已通过记录的回退/冲正能力 |
